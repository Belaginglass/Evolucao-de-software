PROMPT-BASE — Experimento "Evolução do Código Gerado por um LLM ao Longo de Iterações"
Sistema: DogTech (Sistema de Gerenciamento de Adoção — SGA)

Este texto é enviado como contexto fixo em TODAS as solicitações ao Gemini a partir do
incremento I1 (a versão V0 é construída manualmente pelo pesquisador, sem o LLM, e NÃO
usa este prompt-base). A cada incremento, este prompt-base é combinado com o prompt
específico do incremento (I1.txt, I2.txt, ..., I10.txt) e com o estado atual do
código-fonte do projeto.

1. FONTE DE ESPECIFICAÇÃO
- A única fonte de requisitos é o documento "Requisitos_e_Casos_de_Uso.pdf" (SGA/DogTech).
  Não crie, suponha ou complete requisitos funcionais, não funcionais, regras de negócio
  ou casos de uso que não estejam explicitamente no documento ou nos arquivos de
  incremento fornecidos (requisitos/incrementos/I1.md a I10.md).
- O Apêndice C (requisitos/apendice_c_esclarecimentos.md), enviado junto com esta
  solicitação, registra toda decisão de interpretação já tomada para lacunas e
  inconsistências do documento original (ex.: página única de autenticação, busca de
  CEP local). Siga essas decisões; não as questione nem proponha alternativas.
- Quando o documento original for omisso ou ambíguo sobre um detalhe de implementação
  NÃO coberto pelo Apêndice C (ex.: nomes exatos de colunas, formatos de tela não
  especificados), escolha a solução mais simples e direta, e sinalize a suposição feita
  na resposta — essa suposição poderá ser incorporada ao Apêndice C posteriormente.

2. ESCOPO DO INCREMENTO
- Implemente APENAS as funcionalidades descritas no prompt específico deste incremento.
- NÃO implemente funcionalidades previstas para incrementos futuros, mesmo que pareçam
  relacionadas ou convenientes de antecipar.
- Preserve todas as funcionalidades já implementadas nos incrementos anteriores. Não
  remova, reescreva ou altere comportamento existente, exceto quando isso for necessário
  para atender ao requisito do incremento atual ou corrigir um defeito explicitamente
  apontado pelo pesquisador.
- Trabalhe sobre o código-fonte atual fornecido (estado mais recente do repositório Git),
  nunca reconstruindo o sistema do zero.

3. ARQUITETURA E ORGANIZAÇÃO DO CÓDIGO (RNF003 — válido desde o V0)
- Stack fixa do projeto: Java 17, Spring Boot 3.x, Maven, SQLite (via spring-boot-starter
  -data-jpa + driver org.xerial:sqlite-jdbc + hibernate-community-dialects), Thymeleaf
  para as views.
- Siga o padrão MVC: controladores em com.tcc.iterativa.controller, nunca com lógica de
  negócio.
- Camada de serviço (SOA) em com.tcc.iterativa.service: toda regra de negócio e
  orquestração ficam aqui, nunca diretamente no controlador.
- Camada DAO em com.tcc.iterativa.repository, usando interfaces Spring Data JPA.
- Entidades JPA em com.tcc.iterativa.model. DTOs (quando necessários) em
  com.tcc.iterativa.dto. Classes de configuração (beans, segurança, etc.) em
  com.tcc.iterativa.config.
- Não crie camadas, módulos ou abstrações adicionais além dessas quatro, salvo
  necessidade explícita do requisito.

4. REQUISITOS TRANSVERSAIS (válidos desde o V0 — ver requisitos/incrementos/requisitos_transversais.md)
- RNF001 (Criptografia do sistema): toda senha criada ou alterada, em qualquer
  funcionalidade, deve ser armazenada com hash SHA-256 e salt de 8 bits. Use um único
  componente/bean reaproveitado por todas as funcionalidades que manipulam senha —
  nunca implemente essa rotina mais de uma vez.
- RN001 (Validação de e-mail e senha): e-mail deve conter apenas letras A-Z, dígitos 0-9
  e exatamente um "@", sem os caracteres < > " ' / \ : |; senha deve ter no mínimo 8
  caracteres e não conter esses mesmos caracteres proibidos. Use um único validador
  compartilhado por todas as telas que recebem e-mail/senha.
- RNF008 (Campo de ajuda): sempre que um campo de formulário tiver um ícone "?", ele deve
  exibir uma informação de ajuda sobre como preenchê-lo. Siga essa convenção em toda
  tela criada, em qualquer incremento.
- RNF005 (Alterar estados): mudanças de estado do sistema (estado da adoção, processo de
  aceite de um novo usuário administrativo, entre outros previstos no documento) devem
  ser implementadas com o padrão de projeto State — nunca com cadeias de if/else ou
  switch soltos representando o estado.
- RN009 (Gerência de agendas): quando a funcionalidade do incremento exigir uma agenda
  (ex.: ao conceder privilégio administrativo, ao agendar visita, ao agendar prestação de
  serviço), reaproveite um único serviço de agenda. Não implemente lógicas de agenda
  separadas para cada caso de uso.

5. INTERPRETAÇÕES ADOTADAS PARA ESTE EXPERIMENTO
- Página única de autenticação (decisão da seção 3.2 do artigo): embora o <RF001> do
  documento original descreva duas páginas de autenticação (pública/adotante e
  administrativa restrita por URL), este experimento usa UMA ÚNICA página de
  autenticação (login, cadastro e recuperação de senha no mesmo ponto de entrada). O
  redirecionamento por nível de acesso ocorre DEPOIS do login (RN010), não na escolha de
  qual página acessar.
- Busca de CEP (RNF002) sem API externa: em vez de consultar uma API de CEP (Postmon ou
  similar) pela internet, use o arquivo src/main/resources/ceps.csv como fonte local de
  dados de endereço. Esse CSV tem as colunas: cep (8 dígitos, sem hífen), rua, bairro,
  cidade, estado. Ao implementar a busca de CEP (nos incrementos que a utilizam —
  cadastro de usuário e, conforme citado no documento original, UC004), faça a consulta
  a esse arquivo local, carregado como recurso do classpath, em vez de uma chamada HTTP
  externa. Isso evita dependência de rede durante a geração e execução automatizada dos
  testes ao longo do experimento.

===== APÊNDICE C — ESCLARECIMENTOS E DECISÕES DE INTERPRETAÇÃO =====
# Apêndice C — Esclarecimentos e decisões de interpretação

Este apêndice consolida toda decisão de interpretação tomada neste experimento sobre
pontos em que o documento de requisitos original (*Requisitos_e_Casos_de_Uso.pdf*) é
ambíguo, incompleto ou internamente inconsistente. Nenhuma decisão aqui cria um
requisito novo — todas resolvem uma lacuna ou inconsistência já presente no documento
-fonte, de forma explícita e rastreável, conforme a seção 3.2 do artigo
("Eventuais limitações ou decisões presentes na especificação serão registradas, de
modo a preservar a rastreabilidade entre os requisitos e o comportamento observado").

Este arquivo é enviado ao Gemini em toda chamada (seção 8.2 do protocolo de geração),
junto com o prompt-base e o prompt específico do incremento, para que as mesmas
decisões sejam aplicadas de forma consistente em todos os incrementos.

## C.1 — Página única de autenticação (afeta I1 / RF001 / UC001)

O `<RF001>` do documento original descreve duas páginas de autenticação: uma pública
(menu principal, cadastro de adotante) e outra restrita, acessível apenas por URL
direta (cadastro administrativo). Para este experimento, usa-se **uma única página de
autenticação** — login, cadastro e recuperação de senha no mesmo ponto de entrada. O
redirecionamento por nível de acesso ocorre **depois** do login (`<RN010>`), não na
escolha de qual página acessar.

Fonte da decisão: seção 3.2 do artigo. Detalhado em `requisitos/incrementos/I1.md`.

## C.2 — Busca de CEP via arquivo local, sem API externa (afeta I2 / RNF002)

A `<RNF002>` do documento original prevê consultar uma API externa de CEP (Postmon ou
similar). Para este experimento, usa-se o arquivo `Projeto/src/main/resources/ceps.csv`
(colunas: `cep` — 8 dígitos, sem hífen —, `rua`, `bairro`, `cidade`, `estado`) como
fonte local, eliminando a dependência de rede durante a geração e execução
automatizada dos testes ao longo do experimento. A implementação da busca de CEP deve
consultar esse arquivo (carregado do classpath), nunca fazer uma chamada HTTP externa.

Fonte da decisão: decisão do pesquisador durante a construção do V0 (ver
`resultados/V0/registro_V0.md`). Dados do CSV coletados de fontes públicas reais
referentes a Juiz de Fora/MG (sede da SJPA, conforme o histórico de revisão do
documento original).

## C.3 — Lacuna: não existe `RF007` no documento original

A seção 4 (Requisitos Funcionais) do documento original salta de `<RF006>` para
`<RF008>` — não há um `RF007`. Isso não é uma omissão desta extração; é uma lacuna do
próprio documento-fonte. Nenhum requisito foi criado para preencher esse número.

## C.4 — Inconsistência na `<RNF002>`: citação de "UC02 e UC04"

O texto da `<RNF002>` ("Busca de CEP") cita literalmente que a busca de CEP ocorre
"nos cadastros especificados no UC02 e UC04". UC002 (Cadastro) de fato tem campos de
endereço (`<RN002>`). UC004 (Manter Privilégio dos Atores), porém, não possui nenhum
campo de endereço em seus fluxos descritos — a citação ao UC004 é mantida tal como
está no documento original (possível erro de numeração de uma revisão anterior do
documento-fonte), sem reinterpretação. Ao implementar I5 (UC004), **não** é esperado
que exista busca de CEP, a menos que uma revisão futura do documento original
esclareça essa referência.

## C.5 — Inconsistência de numeração na regra citada para geração do token de recuperação de senha (afeta I1)

No fluxo `[FA-1]` do `<UC001>`, o passo 2 cita "RN006" como a regra que define a
geração do token de recuperação de senha (UUID de 32 caracteres, validade de 24h). O
conteúdo descrito corresponde, na verdade, à `<RN005>` ("Trocar senha") — `<RN006>`
trata de "Ordem da listagem de animais", um assunto não relacionado. Para a
implementação, usa-se o conteúdo da `<RN005>` (geração via `UUID.randomUUID()`,
validade de 24h), não o número literal "RN006" citado no texto.

## C.6 — Requisitos sem `RFxxx` numerado, derivados da seção 2.2 (Requisitos dos usuários)

Três funcionalidades não têm um `<RFxxx>` numerado dedicado na seção 4 do documento
original, apenas uma menção na lista de "Requisitos dos usuários" (seção 2.2):

- "Manter página inicial" (afeta I4 / UC009) — `[ATR-01] Manter página inicial.`
- "Manter eventos" (afeta I10 / UC012) — `[ATR-01] Manter eventos.`
- "Manter relatórios" (afeta I10 / UC014) — `[ATR-01] Manter relatórios.` e
  `[ATR-02] Manter relatórios.`

Para essas três, a especificação funcional usada é o próprio caso de uso (UC009,
UC012, UC014) descrito na seção 6 do documento original — não um RF numerado.

## C.7 — `UC014` (Manter relatórios) não especifica quais relatórios devem existir

O documento original diz apenas que "o sistema deverá prover uma página com
relatórios... contendo dados que sejam interessantes para os gestores em específico",
sem listar quais relatórios ou quais dados. Para I10, a implementação deve prover uma
página de relatórios funcional, mas o conteúdo exato de cada relatório é uma decisão de
implementação em aberto — qualquer relatório implementado deve usar apenas dados já
existentes no sistema (ex.: contagem de adoções por estado, animais cadastrados por
espécie), nunca inventar uma fonte de dados nova só para preencher a tela.

# Incremento 8 — Acompanhamento e funcionalidades de pós-adoção

**Caso de uso:** UC010 — Manter pós-adoção

> Fonte: *Requisitos_e_Casos_de_Uso.pdf*, seção 6, p. 64-77.

## UC010 — Manter pós-adoção

**Descrição:** o sistema deve possibilitar que o gestor de adoção avalie o pós-adoção de cada adoção.

**Atores:** Gestor de adoção e adotante.

**Precondições:** Estar autenticado, autorizado e ter passado pelo menos cinco dias após o animal ter sido adotado (conforme `<RN012>`).

**Pós-condições:** Um adotante deverá possuir mais uma avaliação referente à sua adoção cadastrada no sistema.

### Fluxo Básico (condensado)
1. Gestor sinaliza a adoção como "adotado" em `[PRT-16]`.
2. Após 5 dias, sistema habilita "pedir feedback" (gestor, `[PRT-16]`) e "enviar feedback" (adotante, `[PRT-17]`); após 15 dias sem interação de nenhuma parte → `[FA-20]`.
3. Se gestor "pedir feedback" → segue fluxo básico; se adotante "enviar feedback" → `[FA-19]`.
4. Sistema retorna `[PRT-35]`; gestor escreve mensagem e clica "enviar".
5. Sistema envia e-mail ao adotante e notifica no menu "minhas adoções".
6. Adotante acessa a notificação; sistema retorna `[PRT-37]`; adotante responde (podendo anexar imagem) e clica "enviar".
7. Sistema envia e-mail ao gestor e notifica no menu "aprovar adoção".
8. Gestor acessa a notificação ou "ver feedback"; sistema retorna `[PRT-38]`.
9. Gestor classifica o adotante por estrelas; se marcar "sim" para "necessita de mais acompanhamento?", sistema habilita a opção de revogar a adoção — confirmando, altera o estado para "revogado" e notifica o adotante por e-mail. Se "não", gestor responde ao feedback e clica "enviar"; sistema mantém o estado "adotado", salva a avaliação e notifica o adotante.
10. Adotante acessa "minhas adoções" e clica "enviar relato da adoção"; sistema retorna `[PRT-39]`; adotante escreve o relato (podendo anexar imagem) e envia.
11. Sistema salva o relato como pendente de exibição em `[PRT-40]` (página "adotados").
12. Gestor acessa `[PRT-40]`: se "aprovar", sistema exibe o relato publicamente em `[PRT-42]` e o caso de uso se encerra; se "remover", sistema retorna `[PRT-41]` para o gestor escrever o motivo, envia e-mail ao adotante informando a remoção e mantém notificação no menu "adotados" do adotante.
13. Adotante pode acessar `[PRT-42]`/`[PRT-43]` e reescrever o relato, repetindo a etapa de envio.

### Fluxo Alternativo — `[FA-19]` Envio de feedback por parte do adotante
1. Inicia quando o adotante, após 5 dias da adoção aprovada, acessa `[PRT-17]` e clica "enviar feedback".
2. Sistema retorna `[PRT-36]`; adotante escreve e opcionalmente anexa imagem, clica "enviar".
3. Sistema retoma o fluxo básico a partir da notificação ao gestor.

### Fluxo Alternativo — `[FA-20]` Envio de pedido de feedback do sistema
1. Inicia quando, decorridos 15 dias sem interação, o sistema envia e-mail automático ao adotante pedindo feedback.
2. Adotante acessa "minhas adoções" e clica na notificação; sistema retorna `[PRT-36]`.
3. Adotante escreve e opcionalmente anexa imagem, clica "enviar"; sistema retoma o fluxo básico a partir da notificação ao gestor.

### Protótipos referenciados
`[PRT-35]` Pedido de feedback · `[PRT-36]` Envio de feedback · `[PRT-37]` Resposta de pedido de feedback · `[PRT-38]` Visualização da resposta · `[PRT-39]` Envio de relato · `[PRT-40]` Histórico de adotados (administrativo) · `[PRT-41]` Remoção de relato · `[PRT-42]` Página de relatos pública · `[PRT-43]` Motivo da remoção.

INCREMENTO I8 — Acompanhamento e funcionalidades de pós-adoção

Implemente o caso de uso UC010 (Manter pós-adoção), descrito em detalhe no
bloco "REQUISITOS DO INCREMENTO I8" desta mesma solicitação, e nenhuma outra
funcionalidade. Use a entidade Adocao já existente.

Funcionalidades:
- Gestor marca uma adoção (estado AGUARDANDO_VISITA) como "ADOTADO" (transição
  de estado, RN004).
- A partir de 5 dias depois de uma adoção marcada como ADOTADO, o gestor pode
  "pedir feedback" e o adotante pode "enviar feedback" (RN012). Para fins de
  teste manual, NÃO bloqueie rigidamente por data real — adicione um parâmetro
  ou endpoint que permita simular/forçar a contagem de dias (ex.: aceitar a
  troca de feedback mesmo que a diferença de dias seja pequena, OU exponha a
  data da adoção para ser manipulável em teste), para que o fluxo seja
  verificável sem esperar 5 dias de verdade. Documente na resposta qual
  abordagem você escolheu.
- Troca de mensagens (pedir feedback / responder feedback) entre gestor e
  adotante sobre a adoção.
- RF009: ao receber a resposta do adotante, o gestor classifica o adotante por
  estrelas (1 a 5, conforme a escala do documento de requisitos). Se mais de
  um gestor classificar o mesmo adotante, a MENOR nota deve prevalecer.
- RF011: o adotante pode enviar um relato/foto da experiência (Base64, nunca
  BLOB); o relato fica PENDENTE até o gestor aprovar; só então aparece
  publicamente numa página de "adotados". O gestor pode também remover um
  relato já aprovado, informando o motivo; o adotante é notificado.
- RN004: ao final do ciclo, a adoção permanece "ADOTADO" ou pode ir para
  "DEVOLVIDO" ou "REVOGADO" se o gestor indicar necessidade.

Lembre-se das lições anteriores: não use @Lob/BLOB; restrinja rotas de gestor
com hasAnyRole no SecurityConfig; a página pública de "adotados" (relatos
aprovados) deve ficar acessível sem login.

package com.tcc.iterativa.config;

import org.springframework.core.io.ClassPathResource;
import org.springframework.stereotype.Component;

import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import java.util.HashMap;
import java.util.Map;

@Component
public class CepUtils {

    public Map<String, String> buscarCep(String cepInput) {
        if (cepInput == null) return null;
        String cepLimpo = cepInput.replaceAll("\\D", "");

        try {
            ClassPathResource resource = new ClassPathResource("ceps.csv");
            try (BufferedReader reader = new BufferedReader(new InputStreamReader(resource.getInputStream(), StandardCharsets.UTF_8))) {
                String linha;
                boolean primeira = true;
                while ((linha = reader.readLine()) != null) {
                    if (primeira) {
                        primeira = false;
                        continue;
                    }
                    String[] partes = linha.split(",");
                    if (partes.length >= 5) {
                        String csvCep = partes[0].trim();
                        if (csvCep.equals(cepLimpo)) {
                            Map<String, String> endereco = new HashMap<>();
                            endereco.put("cep", csvCep);
                            endereco.put("rua", partes[1].trim());
                            endereco.put("bairro", partes[2].trim());
                            endereco.put("cidade", partes[3].trim());
                            endereco.put("estado", partes[4].trim());
                            return endereco;
                        }
                    }
                }
            }
        } catch (Exception e) {
            // Tratar falha de leitura do CSV
        }
        return null;
    }
}

package com.tcc.iterativa.config;

import org.springframework.stereotype.Component;
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;
import java.util.Base64;

@Component
public class PasswordUtils {

    private static final int SALT_BYTES = 1; // 8 bits = 1 byte

    public String generateSalt() {
        byte[] salt = new byte[SALT_BYTES];
        new SecureRandom().nextBytes(salt);
        return Base64.getEncoder().encodeToString(salt);
    }

    public String hashPassword(String password, String saltStr) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] salt = Base64.getDecoder().decode(saltStr);
            digest.update(salt);
            byte[] hash = digest.digest(password.getBytes(StandardCharsets.UTF_8));
            return Base64.getEncoder().encodeToString(hash);
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException("Erro ao criptografar senha", e);
        }
    }

    public boolean validatePassword(String rawPassword, String saltStr, String storedHash) {
        String newHash = hashPassword(rawPassword, saltStr);
        return newHash.equals(storedHash);
    }

    public boolean validateFormat(String email, String password) {
        if (email == null || password == null) {
            return false;
        }
        // RN001: E-mail deve conter apenas letras A-Z, digitos 0-9 e exatamente um "@", sem < > " ' / \ : |
        // Senha: min 8 caracteres, sem esses mesmos caracteres.
        String emailRegex = "^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,6}$Rs*";
        // Ajuste simples para caracteres proibidos
        String forbiddenChars = "[<>\"'/:|\\\\]";
        
        if (email.matches(".*" + forbiddenChars + ".*")) return false;
        if (password.matches(".*" + forbiddenChars + ".*")) return false;
        
        long atCount = email.chars().filter(ch -> ch == '@').count();
        if (atCount != 1) return false;

        if (password.length() < 8) return false;

        return true;
    }
}

            context.setAuthentication(authentication);
            SecurityContextHolder.setContext(context);

@Controller

    private final UsuarioRepository usuarioRepository;

        this.usuarioService = usuarioService;
        this.usuarioRepository = usuarioRepository;
    }

    @GetMapping("/meus-dados")
    public String exibirMeusDados(Authentication authentication, Model model) {
        if (authentication == null) return "redirect:/login";
        String email = authentication.getName();
        Optional<Usuario> opt = usuarioRepository.findByEmail(email);
        if (opt.isPresent()) {
            model.addAttribute("usuario", opt.get());
            return "auth/meus-dados";
        }
        return "redirect:/login";
    }

    @PostMapping("/meus-dados")
    public String atualizarMeusDados(
            Authentication authentication,
            @RequestParam String nome,
            @RequestParam String cpf,
            @RequestParam LocalDate dataNascimento,
            @RequestParam String telefones,
            @RequestParam String rua,
            @RequestParam String numero,
            @RequestParam(required = false) String complemento,
            @RequestParam String bairro,
            @RequestParam String cidade,
            @RequestParam String estado,
            @RequestParam String cep,
            @RequestParam(required = false) MultipartFile fotoFile,
            @RequestParam String voluntario,
            @RequestParam(required = false) String novaSenha,
            Model model) {
        if (authentication == null) return "redirect:/login";
        String email = authentication.getName();
        try {
            byte[] fotoBytes = (fotoFile != null && !fotoFile.isEmpty()) ? fotoFile.getBytes() : null;
            String token = usuarioService.atualizarDadosPessoais(email, nome, cpf, dataNascimento, telefones, rua, numero, complemento, bairro, cidade, estado, cep, fotoBytes, voluntario, novaSenha);
            model.addAttribute("sucesso", "Dados atualizados com sucesso! E-mail de confirmação simulado com token: /atualizar-senha?token=" + token);
            Optional<Usuario> opt = usuarioRepository.findByEmail(email);
            opt.ifPresent(usuario -> model.addAttribute("usuario", usuario));
        } catch (Exception e) {
            model.addAttribute("erro", e.getMessage());
            Optional<Usuario> opt = usuarioRepository.findByEmail(email);
            opt.ifPresent(usuario -> model.addAttribute("usuario", usuario));
        }
        return "auth/meus-dados";
    }

    public Adocao criarPedidoAdocao(Long animalId, String emailAdotante, boolean termoAceito) throws Exception {
        if (!termoAceito) {

        }
        Optional<Animal> animalOpt = animalRepository.findById(animalId);
        if (animalOpt.isEmpty()) {
            throw new IllegalArgumentException("Animal não encontrado.");
        }
        Animal animal = animalOpt.get();
        if (!"Sim".equals(animal.getDisponivelAdocao()) || "Sim".equals(animal.getEmTratamento()) || "Sim".equals(animal.getPatrimonioTombado())) {
            throw new IllegalArgumentException("Este animal não está disponível para adoção.");
        }

        Optional<Usuario> usuarioOpt = usuarioRepository.findByEmail(emailAdotante);
        if (usuarioOpt.isEmpty()) {
            throw new IllegalArgumentException("Usuário adotante não encontrado.");
        }
        Usuario adotante = usuarioOpt.get();

        // RN007: Gestor não pode adotar seu próprio animal / aprovar próprio pedido

        Adocao adocao = new Adocao(animal, adotante, "AGUARDANDO", LocalDateTime.now());
        return adocaoRepository.save(adocao);
    }

            return adocaoRepository.findByAdotanteOrderByDataPedidoAsc(usuarioOpt.get());

    public List<Adocao> listarFilaAdocao(String emailGestorLogado) {
        Optional<Usuario> gestorOpt = usuarioRepository.findByEmail(emailGestorLogado);
        List<Adocao> todas = adocaoRepository.findAll();
        
        return todas.stream().filter(a -> {
            // RN007: O sistema não deve listar os pedidos de adoção do próprio gestor
            if (gestorOpt.isPresent() && a.getAdotante().getId().equals(gestorOpt.get().getId())) {
                return false;
            }
            return true;
        }).sorted((a1, a2) -> {
            boolean a1Ag = "AGUARDANDO".equals(a1.getEstado());
            boolean a2Ag = "AGUARDANDO".equals(a2.getEstado());
            if (a1Ag && !a2Ag) return -1;
            if (!a1Ag && a2Ag) return 1;
            return a1.getDataPedido().compareTo(a2.getDataPedido());
        }).collect(Collectors.toList());
    }

    public void aprovarAdocao(Long adocaoId, String emailGestor, String disponibilidade) throws Exception {

        Adocao adocao = adocaoOpt.get();
        Optional<Usuario> gestorOpt = usuarioRepository.findByEmail(emailGestor);
        
        // RN007: Gestor não pode aprovar a própria solicitação
        if (gestorOpt.isPresent() && adocao.getAdotante().getId().equals(gestorOpt.get().getId())) {
            throw new IllegalArgumentException("RN007: Um gestor não pode aprovar sua própria solicitação de adoção.");
        }

        adocao.setEstado("AGUARDANDO_VISITA");
        adocaoRepository.save(adocao);
        // RN015: Simular envio de e-mail com disponibilidade
    }

            adocao.setEstado("REPROVADO");

        }

        if (animalOpt.isPresent()) {
            List<Adocao> adocoes = adocaoRepository.findByAnimal(animalOpt.get());
            for (Adocao a : adocoes) {
                if (!a.getId().equals(adocaoExcecaoId) && "AGUARDANDO".equals(a.getEstado())) {
                    a.setEstado("REPROVADO");
                    adocaoRepository.save(a);
                }
            }
        }
    }

        Optional<Animal> animalOpt = animalRepository.findById(animalId);

import java.util.Map;

@Service
public class UsuarioService {

    private final UsuarioRepository usuarioRepository;
    private final PasswordUtils passwordUtils;
    private final CepUtils cepUtils;

    public UsuarioService(UsuarioRepository usuarioRepository, PasswordUtils passwordUtils, CepUtils cepUtils) {
        this.usuarioRepository = usuarioRepository;
        this.passwordUtils = passwordUtils;
        this.cepUtils = cepUtils;
    }

    public Usuario cadastrar(String email, String senha, String papel, String nome, String cpf, LocalDate dataNascimento, String telefones, String rua, String numero, String complemento, String bairro, String cidade, String estado, String cep, byte[] fotoBytes, String voluntario) throws Exception {
        if (!passwordUtils.validateFormat(email, senha)) {
            throw new IllegalArgumentException("E-mail ou senha inválidos segundo as regras de formato.");
        }
        if (usuarioRepository.findByEmail(email).isPresent()) {
            throw new IllegalArgumentException("E-mail já cadastrado.");
        }
        if (cpf != null && !cpf.isEmpty() && usuarioRepository.findAll().stream().anyMatch(u -> cpf.equals(u.getCpf()))) {
            throw new IllegalArgumentException("CPF já cadastrado.");
        }
        if (telefones == null || telefones.trim().isEmpty()) {
            throw new IllegalArgumentException("Pelo menos um número de telefone deve ser inserido.");
        }

        String salt = passwordUtils.generateSalt();
        String hash = passwordUtils.hashPassword(senha, salt);

        String fotoStr = (fotoBytes != null && fotoBytes.length > 0) ? Base64.getEncoder().encodeToString(fotoBytes) : null;

        Usuario usuario = new Usuario(email, hash, salt, papel);
        usuario.setNome(nome);
        usuario.setCpf(cpf);
        usuario.setDataNascimento(dataNascimento);
        usuario.setTelefones(telefones);
        usuario.setRua(rua);
        usuario.setNumero(numero);
        usuario.setComplemento(complemento);
        usuario.setBairro(bairro);
        usuario.setCidade(cidade);
        usuario.setEstado(estado);
        usuario.setCep(cep);
        usuario.setFoto(fotoStr);
        usuario.setVoluntario(voluntario);

        return usuarioRepository.save(usuario);
    }

    // Compatibilidade com testes antigos de I1
    public Usuario cadastrar(String email, String senha, String papel) throws Exception {
        return cadastrar(email, senha, papel, "Nome Teste", "00000000000", LocalDate.now().minusYears(20), "99999-9999", "Rua A", "10", "", "Bairro B", "Cidade C", "MG", "36050000", null, "Sim");
    }

    public Optional<Usuario> autenticar(String email, String senha) {
        Optional<Usuario> opt = usuarioRepository.findByEmail(email);
        if (opt.isPresent()) {
            Usuario u = opt.get();
            if (passwordUtils.validatePassword(senha, u.getSalt(), u.getSenha())) {
                return Optional.of(u);
            }
        }
        return Optional.empty();
    }

    public String gerarTokenRecuperacao(String email) {
        Optional<Usuario> opt = usuarioRepository.findByEmail(email);
        if (opt.isPresent()) {
            Usuario u = opt.get();
            String token = UUID.randomUUID().toString().replace("-", "");
            u.setTokenRecuperacao(token);
            u.setValidadeToken(LocalDateTime.now().plusHours(24));
            usuarioRepository.save(u);
            return token;
        }
        return null;
    }

    public boolean alterarSenhaComToken(String token, String novaSenha) {
        Optional<Usuario> opt = usuarioRepository.findByTokenRecuperacao(token);
        if (opt.isPresent()) {
            Usuario u = opt.get();
            if (u.getValidadeToken() != null && u.getValidadeToken().isAfter(LocalDateTime.now())) {
                if (!passwordUtils.validateFormat(u.getEmail(), novaSenha)) {
                    return false;
                }
                String salt = passwordUtils.generateSalt();
                u.setSenha(passwordUtils.hashPassword(novaSenha, salt));
                u.setSalt(salt);
                u.setTokenRecuperacao(null);
                u.setValidadeToken(null);
                usuarioRepository.save(u);
                return true;
            }
        }
        return false;
    }
    
    public Optional<Usuario> buscarPorToken(String token) {
        Optional<Usuario> opt = usuarioRepository.findByTokenRecuperacao(token);
        if (opt.isPresent() && opt.get().getValidadeToken() != null && opt.get().getValidadeToken().isAfter(LocalDateTime.now())) {
            return opt;
        }
        return Optional.empty();
    }

        Optional<Usuario> opt = usuarioRepository.findByEmail(emailAtual);
        if (opt.isEmpty()) {
            throw new IllegalArgumentException("Usuário não encontrado.");
        }
        Usuario u = opt.get();
        
        if (nome != null) u.setNome(nome);
        if (cpf != null) u.setCpf(cpf);
        if (dataNascimento != null) u.setDataNascimento(dataNascimento);
        if (telefones != null) u.setTelefones(telefones);
        if (rua != null) u.setRua(rua);
        if (numero != null) u.setNumero(numero);
        if (complemento != null) u.setComplemento(complemento);
        if (bairro != null) u.setBairro(bairro);
        if (cidade != null) u.setCidade(cidade);
        if (estado != null) u.setEstado(estado);
        if (cep != null) u.setCep(cep);
        if (fotoBytes != null && fotoBytes.length > 0) {
            u.setFoto(Base64.getEncoder().encodeToString(fotoBytes));
        }
        if (voluntario != null) u.setVoluntario(voluntario);

        if (novaSenha != null && !novaSenha.isEmpty()) {
            if (!passwordUtils.validateFormat(u.getEmail(), novaSenha)) {
                throw new IllegalArgumentException("Nova senha fora do formato exigido.");
            }
            String salt = passwordUtils.generateSalt();
            u.setSenha(passwordUtils.hashPassword(novaSenha, salt));
            u.setSalt(salt);
        }

        u.setDataUltimaAlteracao(LocalDateTime.now());
        String token = UUID.randomUUID().toString().replace("-", "");
        u.setTokenRecuperacao(token);
        u.setValidadeToken(LocalDateTime.now().plusHours(24));

        usuarioRepository.save(u);
        return token;
    }

    public List<Usuario> listarUsuariosAdministrativos(String busca, String cargoFiltro) {
        List<Usuario> todos = usuarioRepository.findAll();
        return todos.stream().filter(u -> {
            boolean ehAdmin = "DIRETOR_GERAL".equals(u.getPapel()) || "GESTOR_ADOCAO".equals(u.getPapel()) || "ADMIN".equals(u.getPapel());
            if (!ehAdmin) return false;

            if (busca != null && !busca.trim().isEmpty()) {
                String b = busca.toLowerCase();
                boolean matchNome = u.getNome() != null && u.getNome().toLowerCase().contains(b);
                boolean matchEmail = u.getEmail() != null && u.getEmail().toLowerCase().contains(b);
                if (!matchNome && !matchEmail) return false;
            }

            if (cargoFiltro != null && !cargoFiltro.trim().isEmpty()) {
                if (!cargoFiltro.equals(u.getPapel())) return false;
            }

            return true;
        }).collect(Collectors.toList());
    }

    public void alterarPrivilegios(Long usuarioId, String novoPapel, String novoStatus) {
        Optional<Usuario> opt = usuarioRepository.findById(usuarioId);
        if (opt.isPresent()) {
            Usuario u = opt.get();
            u.setPapel(novoPapel);
            u.setStatusAdmin(novoStatus);
            usuarioRepository.save(u);
        } else {
            throw new IllegalArgumentException("Usuário não encontrado.");
        }
    }

    public void excluirAcessoAdministrativo(Long usuarioId) {
        Optional<Usuario> opt = usuarioRepository.findById(usuarioId);
        if (opt.isPresent()) {
            Usuario u = opt.get();
            u.setPapel("ADOTANTE");
            u.setStatusAdmin(null);
            usuarioRepository.save(u);
        }
    }
}

      {"caminho": "src/main/java/com/tcc/iterativa/.../Foo.java",
       "acao": "criar" | "modificar" | "remover",
       "conteudo": "<conteúdo TEXTUAL COMPLETO do arquivo, já com o resultado final;"
                   " omitido/vazio quando acao=remover>"}
    ]
  }
- "caminho" é relativo à raiz do projeto Spring Boot (Projeto/), com barras "/",
  nunca ".." nem caminho absoluto. Deve começar LITERALMENTE com "src/" (incluindo
  "src/main/java/" para código Java — nunca omita esse prefixo) ou ser exatamente
  "pom.xml" — não modifique nenhum outro arquivo.
  Exemplo de "caminho" CORRETO para uma classe nova no pacote config (string única,
  sem quebra de linha): "src/main/java/com/tcc/iterativa/config/Exemplo.java"
  Exemplo INCORRETO (NÃO faça isso — falta o prefixo "src/main/java/"):
  "com/tcc/iterativa/config/Exemplo.java"
- "conteudo" é o arquivo INTEIRO já modificado (não um diff, não um trecho) — para
  "modificar", repita também as partes que não mudaram.
- CRÍTICO — "conteudo" precisa ser uma string JSON válida: todo caractere de aspas
  duplas (") que apareça DENTRO do código (ex.: um literal String do Java como
  @Table(name = "usuarios"), ou um atributo HTML como title="texto") DEVE ser
  escapado como " no JSON. Toda quebra de linha deve ser 
 (não uma quebra de
  linha literal). Todo backslash deve ser \. Isso é o erro mais comum — revise
  mentalmente cada "conteudo" antes de responder, caractere por caractere nas
  aspas, procurando aspas internas não escapadas.
  Exemplo CORRETO (trecho de "conteudo" de um arquivo Java, dentro do JSON):
  "conteudo": "@Table(name = "usuarios")
public class Usuario {
..."
  Exemplo INCORRETO (quebra o JSON — NÃO faça isso):
  "conteudo": "@Table(name = "usuarios")
public class Usuario {
..."
- Não gere um unified diff. Não inclua texto explicativo dentro do bloco ```json```.
  Qualquer observação, suposição ou lista de requisitos atendidos deve vir DEPOIS do
  bloco, em texto normal.
- Ao final, fora do bloco de código, liste: (a) arquivos criados/modificados/
  removidos; (b) os identificadores de requisitos atendidos (RF/RNF/RN); (c)
  suposições feitas.
