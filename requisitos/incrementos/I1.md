# Incremento 1 — Autenticação e controle inicial de acesso

**Caso de uso:** UC001 — Autenticação

> Fonte: *Requisitos_e_Casos_de_Uso.pdf* (Levantamento de Requisitos — DogTech/SGA), seção 6, p. 19-24.

## UC001 — Autenticação

**Descrição:** o sistema deve possuir uma página para acessar a área privada, onde é possível se cadastrar, autenticar-se e recuperar senha. A autenticação é feita por e-mail e senha, validados conforme `<RN001>`. Existem duas páginas de autenticação (RF001): uma pública, acessível pelo menu, para cadastro de adotante; outra acessível apenas via URL direta, para cadastro administrativo.

**Atores:** Não se aplica (visitante não autenticado).

**Precondições:** Não estar autenticado.

**Pós-condições:** Recuperar o acesso ao sistema **ou** criar novo usuário no sistema.

### Fluxo Básico
1. Ator acessa a página de autenticação do sistema.
2. Sistema retorna `[PRT-1]` (Autenticação).
3. Se o ator clicar em "esqueceu sua senha?" → segue `[FA-1]`. Se preencher e-mail/senha e clicar "Entrar" → continua o fluxo básico.
4. Sistema valida os dados conforme `<RN001>`; se inválidos → `[FE-1]`. Se válidos, retorna a página inicial conforme o privilégio do ator: administrativo → `[PRT-2]`; adotante → `[PRT-3]` (menus diferentes). A escolha do conteúdo exibido nessas páginas segue `<RN010>`.

### Fluxo Alternativo — `[FA-1]` Recuperar senha
1. Ator preenche seu e-mail e clica "recuperar" (`[PRT-4]`).
2. Sistema busca o registro pelo e-mail; se existir, gera um identificador único (token) e salva junto às informações do ator, enviando um link por e-mail para `[PRT-5]`.
3. Ator acessa o e-mail e abre o link.
4. Sistema valida se o token ainda está dentro do prazo de validade; se expirado, informa o ator; se válido, retorna `[PRT-5]`.
5. Ator preenche a nova senha e clica "enviar".
6. Sistema localiza o usuário pelo token, salva a nova senha no banco e retorna para `[PRT-1]`.

### Fluxo Alternativo — `[FA-2]` Primeiro acesso via cadastro automático
1. Usuário com adoção cadastrada manualmente no sistema acessa a página de login.
2. Sistema retorna `[PRT-1]`.
3. Adotante preenche e-mail e a senha gerada automaticamente, clica "entrar".
4. Sistema verifica os dados; se incorretos → `[FE-1]`; se corretos, direciona para `[PRT-5]` para cadastro de nova senha.
5. Adotante digita a nova senha e clica "enviar".
6. Sistema salva a nova senha e direciona o adotante para a página inicial `[PRT-3]`.

### Fluxo de Exceção — `[FE-1]` Validação
1. Inicia na tentativa de validação dos campos de entrada submetidos.
2. Sistema retorna à tela atual mantendo os valores preenchidos e adiciona um alerta em cada campo preenchido incorretamente, informando a forma correta de preenchimento.

### Protótipos de tela referenciados (não reproduzidos aqui — ver documento original)
`[PRT-1]` Autenticação · `[PRT-2]` Tela inicial administrativa · `[PRT-3]` Tela inicial do adotante · `[PRT-4]` Recuperação de senha · `[PRT-5]` Inserção de nova senha.

## Requisito Funcional relacionado

**`<RF001>` Autenticação**
> "O sistema deve possuir duas páginas para autenticação, em ambas deverá ser possível autenticar-se, recuperar senha e cadastrar-se, porém uma só será acessada diretamente por uma URL e outra ficará disponível no menu principal do site. A página que ficará acessível apenas via URL deverá fornecer um cadastro administrativo e a outra um cadastro apenas de adotante. A autenticação será por meio de e-mail e senha em ambas páginas de autenticação."

### Decisão de interpretação adotada no experimento (seção 3.2 do artigo)
A seção 3.2 da metodologia do artigo (*artigo_sbc*) registra explicitamente: *"O desenvolvimento será realizado a partir de uma única página de autenticação, conforme a interpretação definida para o requisito correspondente."* Ou seja, para este experimento o `<RF001>` é implementado com **uma única página de autenticação** (login, cadastro e recuperação de senha no mesmo ponto de entrada), em vez das duas páginas distintas (pública/adotante e administrativa restrita por URL) descritas literalmente no documento original. O texto do requisito acima é mantido na íntegra por fidelidade e rastreabilidade ao documento-fonte; a simplificação para uma única página é uma decisão metodológica do experimento, não uma alteração do requisito original. O fluxo básico do UC001 descrito nesta seção já é compatível com essa interpretação, pois a distinção de menu/redirecionamento por privilégio ocorre **depois** do login, via `<RN010>`, e não na escolha de qual página de login acessar.

## Regras de Negócio relacionadas

**`<RN001>` Validação de e-mail e senha**
> "1. E-mail: a. Conter apenas letras de A à Z; b. Números de 0 a 9; c. Uma ocorrência do caractere @; d. Não possuir nenhum dos caracteres a seguir: <, >, \", ', /, \\, :, |. 2. Senha: a. Conter no mínimo oito (8) caracteres; b. Não possuir nenhum dos caracteres a seguir: <, >, \", ', /, \\, :, |."

**`<RN005>` Trocar senha**
> "O identificador único (token) para troca de senha deverá ser gerado utilizando do método randomUUID da classe UUID do pacote útil do Java, este método retornará uma String com 32 caracteres única. Este token deve ser válido por apenas 24 horas, para isso deverá ser salvo no banco o dia da alteração de senha junto ao token gerado."

**`<RN010>` Escolha de dados na tela inicial do sistema** *(detalhada no Incremento 4 — UC009; citada aqui por reger a tela de destino pós-login)*
> "Na tela inicial do sistema que pode ser vista nos protótipos [PRT-2] e [PRT-3] o sistema deverá escolher aleatoriamente os serviços, campanhas, valores para doação e animais a serem exibidos."

## Observações de fidelidade ao documento original
- No passo 2 do fluxo `[FA-1]`, o documento cita "RN006" como a regra que define a geração do token de recuperação de senha. O conteúdo descrito (UUID de 32 caracteres, validade de 24h) corresponde, no entanto, à regra `<RN005>` ("Trocar senha"), já que `<RN006>` trata de "Ordem da listagem de animais" — um assunto não relacionado. Optou-se por manter aqui a referência a `<RN005>`, por coerência de conteúdo, sinalizando a inconsistência de numeração encontrada no documento-fonte sem alterar o teor do requisito.
- A existência de duas páginas de autenticação distintas (ver `<RF001>` acima) **não** é implementada neste experimento — ver "Decisão de interpretação adotada no experimento" nesta mesma seção, conforme definido na seção 3.2 do artigo.
